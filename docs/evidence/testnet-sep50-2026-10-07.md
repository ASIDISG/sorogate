# A real SEP-50 collection on Testnet, 2026-10-07

**Label: Recorded.** One manual run of `packages/sdk/scripts/testnet-sep50.ts` against the **public Testnet deployment**
of the policy contract ([`../DEPLOYMENT.md`](../DEPLOYMENT.md)). Raw output, including every transaction hash:
[`testnet-sep50-2026-10-07.json`](testnet-sep50-2026-10-07.json). It is not part of CI, because it uses a public network.

Step labels: **Transaction** is sent to the network and applied (a failed transaction was applied, and failed);
**Simulation** is asked of the network without applying anything; **Reading** is a value read from the network.

## What was checked

`NftBalance` reads `balance(owner)` of a collection and expects a `u32`. SEP-50 is a Draft (version 0.1.0). Its text
defines `balance` as returning a type called `Balance`, which it describes only as "an unsigned integer", usually the same
type as the token id. It never says `u32`. So whether the condition works against a real collection was an open question,
and this run answers it for one real implementation.

## Result

**All 29 steps happened as expected.**

- **The real collection answers `balance(owner)` with a `u32`** (the raw XDR type was `scvU32`), so the condition's
  assumption holds for this implementation.
- **The contract and the TypeScript model gave the same decision in every comparison** (10 of 10: holders, a non-holder,
  an account that does not exist, a threshold of 1 and of 2, before and after a transfer, and the fungible-token case).
- **Eligibility follows current ownership, not history.** After alice sent a token to carol, the policy that needed two
  denied alice and the one that needed one allowed carol. A claim bob signed while he owned a token was sent after he gave
  it away, and the consumer refused it on the network: the transaction was applied and failed with `BelowMinimum`
  (contract error 11). Bob was not paid. Dave, who received the token, claimed and was paid.
- **An account that owns nothing, or does not exist, is `BelowMinimum`, not `BalanceUnavailable`.** This collection
  returns 0 for any address. That differs from a Stellar asset contract, which raises an error for an account with no
  trustline and so gives `BalanceUnavailable` (see `spec/SPEC.md`).
- **A condition pointed at the wrong kind of contract fails closed.** A fungible token answers `balance` with an `i128`
  (`scvI128`, recorded). The contract denied with `BalanceUnavailable`, and so did the model.

## What it does not show

- **One implementation of SEP-50.** OpenZeppelin's `nft-sequential-minting` example at one release. Its `consecutive` and
  `enumerable` variants, and every other collection that exists or will exist, were not tried. Whether other
  implementations also return a `u32` is open; one that uses a wider unsigned type is treated as `BalanceUnavailable`, by
  design, and that was tested with a fixture, not with a real collection.
- **The collection is not a pre-existing one that other people use.** It is a real SEP-50 implementation, deployed for
  this run from OpenZeppelin's source. No collection somebody else deployed and operates was checked, so nothing here
  shows how the condition behaves against infrastructure we do not control.
- **The collection was built with a different soroban-sdk** from this repository's contracts (26.1.0 against 28.0.0). It
  was the release's own, as OpenZeppelin ships it.
- **Costs.** This run does not measure what an `NftBalance` condition costs.
- **Contract accounts (`C...`) as holders** were not tried.
- It is one run (plus the stopped ones). It found nothing wrong with the condition, which does not show that nothing is
  wrong.
