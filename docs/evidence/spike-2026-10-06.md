# Measurements taken before the contract was written, 2026-10-06

**Label: Recorded.** Throwaway contracts and a throwaway key on Stellar Testnet (protocol 29), used to settle questions
the design depended on. The experiment's code was not kept; the numbers below are what it produced. Several of them
are cited by [`spec/SPEC.md`](../../spec/SPEC.md) and [`docs/THREAT_MODEL.md`](../THREAT_MODEL.md).

Build tooling fact found on the way: soroban-sdk 28.0.0 refuses a plain `cargo build` ("requires stellar-cli v25.2.0+
to build a contract; build with `stellar contract build`").

## 1. What time does a contract see?

| Where | Observation (4 simulations, 3 real transactions) |
| --- | --- |
| Simulation | `ledger().timestamp()` equalled the close time of the **latest closed ledger** every time (difference 0 s), and `sequence()` equalled the latest ledger number |
| Execution | `timestamp()` equalled the close time of **the ledger the transaction was applied in** (difference 0 s) |

A simulation sees the last closed ledger; the transaction it predicts is applied in a later one (here 1 to 5 ledgers
later, about 5 seconds each). A time-window boundary can flip between simulating and submitting.

## 2. What does `try_invoke_contract` catch?

Status: 0 ok, 1 the called contract raised an error, 2 host error, 3 return value of the wrong type.

| Case | Result |
| --- | --- |
| Token returns `i128` | `(0, 100)` |
| Token returns `u64` where `i128` is expected | `3` (caught) |
| Token panics | `1` (caught) |
| Valid contract address with no contract deployed | `1` (caught) |
| Token contract with no `balance` function | `1` (caught) |
| Token burns its whole budget | **Not caught**: the whole simulation fails with `Error(Budget, ExceededLimit)` |
| Token address is an **account** (`G...`) | **Not caught**: the whole call fails with `Error(Object, InvalidInput)` |
| NFT shape: `u32` returned, decoded as `u32` | `(0, 100)` |
| NFT shape: `i128` or `u64` returned, decoded as `u32` | `3` (caught) |

Consequences: a budget-burning token and a non-contract address abort the whole transaction instead of being denied.
The second is avoided by checking when a policy is written that every address is a deployed contract
(`Address::executable()`). The first cannot be caught.

## 3. Re-entry

A token that tried to call back into the contract calling it received a failure (its inner call did not return the
expected value). Re-entry into the calling contract was refused. What was observed is "the inner call did not
succeed", not the exact error code.

## 4. `Address::executable()` as a guard

A second probe checked `executable()` before calling:

| Token address | Guarded result |
| --- | --- |
| A funded account | refused cleanly (unguarded: whole call aborts) |
| A nonexistent account | refused cleanly |
| A contract address with nothing deployed | refused cleanly |
| A WASM contract | called normally |
| A Stellar asset contract | called normally |
| The native asset's contract | called normally |

Cost of the check: about 13,500 instructions on a WASM token and 20,000 on a Stellar asset contract, per condition.

## 5. A Stellar asset contract's `balance` in edge cases

| Case | Result |
| --- | --- |
| Account with **no trustline** for the asset | **Contract error #13, "trustline entry is missing"** (not 0) |
| Account that does not exist | Same error #13 |
| Native asset's contract, account does not exist | Contract error #6, "account entry is missing" |
| A `C...` address | `0` |
| The asset's own issuer | `9223372036854775807` (`i64::MAX`) |

"This address does not hold the asset" is normally an *error* for a classic asset, not a zero.

## 6. Cost of N token reads (simulation, instructions; per-transaction limit 400,000,000)

Overhead with zero reads: 392,481 instructions.

| N | Small WASM tokens, distinct | Stellar asset contracts, distinct |
| --- | --- | --- |
| 1 | 704,680 | 478,796 |
| 4 | 1,620,848 | 742,382 |
| 8 | 2,880,286 | 1,098,684 |
| 16 | 5,418,264 | 1,850,552 |

About 310,000 instructions per small WASM token and 90,000 per asset contract. A large production-style token was not
measured; VM start-up cost grows with the size of the contract, so treat the WASM figures as a floor. The footprint
grows by one entry per distinct token (19 entries at N=16, against a limit of 400).

## 7. Network limits read on the day

Read with stellar-cli 27.1.0 (it warned it supports protocol 27 while the network ran 29, so some settings may be
missing): per transaction 400,000,000 instructions, 41,943,040 bytes of memory, 200 disk-read entries, 400 footprint
entries, 200 write entries; a contract-data entry at most 65,536 bytes; events at most 16,384 bytes per transaction;
maximum time to live 3,110,400 ledgers (about 180 days); minimum for a persistent entry 120,960 ledgers (7 days).

## 8. Message signing

The SDK's `Keypair.signMessage` reproduces the SEP-53 test vector exactly and `verifyMessage` accepts it, so a server
can verify SEP-53 signatures with the SDK directly. Whether a given wallet signs the same bytes was **not** checked
(a one-page tester was prepared and has not been run).
